# Security policy

## Report privately

On the public repository, use **Security → Report a vulnerability** to open a private advisory with the maintainers. Do not put exploit details, credentials, preference dumps, notification text, contact data, screenshots of real accounts or device identifiers in a public issue or pull request.

Private reports go to the project maintainer through GitHub, once reporting is enabled on the public repository. If private reporting is unavailable, open a neutral issue requesting a private reporting channel, without vulnerability details, and wait for that channel. There is no separate security email and no response-time commitment. **Release owner: enable and test private vulnerability reporting before announcing the repository.**

Include the affected commit/build type, Android version, required permissions, impact, and minimal reproduction using synthetic data. Describe the trust boundary crossed and whether the behavior also occurs in a release build. Share a patch privately when possible. Coordinate disclosure with the maintainers; do not test against other people's accounts or devices.

## Scope and support

This is an experimental launcher, not a hardened assistant. Only the current development branch is maintained; there are no supported production releases or security backport guarantees yet. In scope: credential leakage, unintended notification/screen capture, exposed Android components, intent abuse, approval bypass, unauthorized app control, and data exposure through storage, logs or network requests.

Accessibility and Shizuku intentionally permit powerful app control. The model and outside app/web text are untrusted. Label-based commit detection is incomplete; banking, payments, identity documents and login automation remain out of scope for use. Reports of bypasses still matter. Protected apps (Shizuku, Misura, catalogued authenticators/password managers; catalogued banking/payment apps default off; owner-blocked apps) are refused at the agent's entry points only; mid-task redirects into a protected app are not caught. See the README. Read [the audit](docs/OSS_AUDIT.md) for unresolved risks.

## Credentials and local data

- Use a dedicated test device, trusted adb host and your own least-privileged Cloud project with spending limits. Prefer short-lived tokens. Never distribute an APK, emulator image or app-data archive with credentials configured.
- Credentials (Vertex token or service-account JSON, Gemini/OpenAI/Anthropic API keys and optional Exa/Tavily/Context.dev keys), briefing and notes use the shared AES-256-GCM helper in app-private `brain` SharedPreferences. The per-install key is generated in Android Keystore and is non-exportable; no user-authentication gate blocks background operation. Plaintext preferences migrate on first read, with no deletion before successful persistence. Debug provisioning writes through the helper and still requires shell/system `DUMP`. Backup/transfer stay excluded. This does not protect a compromised running app, authorized adb access, provider copies or old backups; local credential onboarding is available; independent Cloud-project setup remains unverified.
- Non-exported local setup uses password fields and a screenshot-protected window, never preloads saved keys, and keeps unsaved text out of saved UI state. Save performs offline validation and uses one preferences commit; blank secret fields keep existing keys. Existing values are restored if persistence reports failure. Keys never enter agent prompts through setup. Model and optional search credentials are scoped to their respective services. Local validation cannot establish Cloud IAM, billing, or provider availability. An explicit setup project overrides legacy project resolution only after Save.
- The selected Vertex, Gemini, OpenAI or Anthropic account receives model inputs, including screen text for app control. Each turn captures its provider, model, credentials and optional services. A web lookup sends the question/date to the selected external service first, if configured, then uses the same model account for native search on operational failure. An installed browser can receive the query when direct lookup is unavailable. Native search can be billed even if attribution requirements prevent displaying the result. Google responses requiring search-suggestion HTML fall back to the browser. Separate Google Cloud access enables direct Places services.
- OpenAI uses stateless requests. Visible history travels to a newly selected provider on subsequent turns. Opaque reasoning belongs to its client. Local deletion and stateless requests do not establish provider-side retention. An interrupted tool can have an unknown outcome. Verify it in the target app before retrying.
- Service-account files are signing credentials, not harmless configuration. Do not relax an organization's key policy to run this demo. Use the short-lived-token path when key creation is disallowed. Restrict access to only the APIs/project needed and revoke credentials if exposed or the test phone is lost.
- Provisioning scripts use adb arguments; credentials can be visible to trusted local/device debugging tools. Do not enable shell tracing, record the provisioning terminal, or run them on shared/untrusted hosts.
- Owner decision: notification capture allows all packages except protected apps (README) after Android grants listener access, skipping Misura itself and existing noise filters. An empty-by-default exact-package block list can stop future collection/live replies for individual apps; it does not delete history or limit separately requested accessibility work. Old allow-list preferences do not gate upgraded installs. Debug command uses `notifications --es app <package> --ez blocked true`; `false` restores access. No first-run package opt-in; the local settings screen edits the same block list, including saved blocked apps without a current notification.
- On-demand `read_notifications` exposes only current notifications from unblocked apps, excluding Misura itself and group summaries. It does not dismiss, reply or mark read. Selected title/text goes to the configured model and into normal encrypted session/turn history, which has no automatic expiry; this is separate from 14-day inbox retention. No raw extras/actions or new notification-history store are exposed by the tool.
- Room JSON payloads (including message/task/session text), item JPEGs and item title/price files encrypt on write using the same versioned helper. Legacy plaintext reads remain compatible and re-encrypt on write. Query metadata (ids, packages, times, states) remains visible; conversation/seen lookup ids use SHA-256 digests, which reveal equality and permit guessing low-entropy values. This is field/file encryption, not whole-database encryption or secure erasure of old SQLite pages/files.
- Availability policy: unavailable Keystore/encryption falls back to plaintext writes with a content-free debug warning (also supports emulators/Robolectric). Ciphertext authentication failures, unknown versions and unavailable decryption keys return no value, never ciphertext-as-plaintext; rows/files/preferences stay intact. Notes and Room task/session/approval/attempt/expectation replacements refuse changes while their stored value is unreadable; Room checks and writes share a transaction, including send claims. New records retain the documented plaintext-write fallback. A lost key cannot decrypt old data; the helper never replaces an existing key alias.
- Inbox answer text older than 14 days is pruned by message timestamp on startup and inserts; seen ids expire 14 days after observation, and expectations 14 days after expiry. Legacy seen ids get one window from upgrade because their timestamps were not stored. `INBOX_RETENTION_MS` is the single duration constant. Sessions/controller evidence have no automatic expiry; user notes are retained until explicitly changed/forgotten (prompt length is still bounded). Item files keep their existing seven-day cleanup. Clear app storage in Android settings to remove local data, and revoke Cloud credentials separately.
- Accessibility still reads target apps and sends relevant screen text/context to the model. At-rest encryption does not protect screenshots sent to a model or provider copies; current `use_app` calls send text only, with cropped screenshots stored locally. Password-node redaction cannot redact secrets from arbitrary images or ordinary text. Local deletion does not erase provider copies or old backups.
- Debug probe output contains metadata only, capped at 256 KiB with records older than 24 hours removed on the next cleanup/read/write. Release produces no probe output and purges legacy probe files on startup. Metadata diagnostics stay enabled in the debug variant with `-Pfast`; detailed logs and raw extras still require `BuildConfig.DEBUG`. Diagnostic activities, receiver and report writer are absent from release source sets. Other debug diagnostics can contain private task/screen content; review/redact them before sharing.

## Memory and message routing

Memory writes require an isolated authorization call to the same configured model using genuine owner utterances and the current date only. Briefing, learned notes, tool/app results, generated choices/sent text and the main model’s proposed arguments cannot authorize new fact text. Cross-session forget/correct requests may separately match an owner-authorized topic to an index in the existing bounded note set; a selected full note must still exist at mutation time. Invalid or ambiguous selection does not write. Valid no-match permits an independently authorized new fact, preserving corrections to briefing-only information. Model interpretation and semantic note selection remain fallible; old poisoned notes can still mislead target selection. Existing encryption/retention and same-turn outside-text refusal stay in place; no extra consent screen or model downgrade is added.

Quick-reply drafts can bind an explicitly named app’s exact package and never silently fall back when a supplied binding is malformed or unsupported. Controls/bidi are removed from displayed app labels; colliding or empty labels include the real package in the existing approval field. The package/key/digest binding remains authoritative. App names and notification sender names are supplied by installed apps and do not authenticate a person or brand; arbitrary Unicode visual lookalikes and an owner approving an untrusted installed app remain risks.

## Publishing checklist

Publish a reviewed source export, never a workspace ZIP. Ignored files/build outputs can contain personal data. Verify the exact outgoing Git history separately; this audit did not inspect historical blobs. Review [third-party notices](THIRD_PARTY_NOTICES.md), configure private reporting, run release/device checks, and resolve the audit's owner decisions before distributing a usable release.
